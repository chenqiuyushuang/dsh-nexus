# V0.9 功能面审计：专家团「删除清单」的真实影响面

背景：十五人专家团在第一轮评审里给过一份删除清单（vector 含 RRF、integrator、skill-compiler、
`atom.embedding`、goal/todo capture、`projectionState` 死代码）。本文核对**每一项到底还能不能被触发**，
以及删掉的影响面 —— 因为「删代码」和「砍功能」是两件事。

## 结论速览

## 证据细节

- `~/.dsh/nexus/` 只有 `MEMORY.md` 与 `USER.md`，**没有 `skills.draft/`** → skill-compile 从未运行；
- `~/.dsh/settings.yaml` 与 profile 的 `cordis.yml` 里**没有任何 vector/integrator 配置**；
- `vector` 的解析逻辑：不传、传 false、传 true 都得到 `false`（传 true 还会 warn「缺少 endpoint/model/dim」），
  即**默认永不启用**，且需要一个本部署里并不存在的外部 embedding 服务；
- 三个模块合计 **288 行、零测试覆盖**（`grep -rln` 在 tests/ 下无命中）。

## 我的建议（分两步，风险不同）

**第一步（低风险，已做）**：删除 `atom.embedding` 字段与 `atomEmbeddingSchema`。
理由：无任何读写路径，磁盘上没有任何记录带该字段，schema 非 strict → 删除不影响存量数据解析。

**第二步（需要你点头）**：删除 `vector` 检索。
理由：默认关闭、需要外部 embedder、零测试、零使用；它带来的是配置面上的 5 个旋钮（endpoint/model/dim/topK/rrfK）
与一条永远走不到的分支。**代价**：将来想接本地/远端 embedding 时要重新实现（可从 git 历史取回）。

**第三项（我倾向保留，理由是路线而非代码）**：`integrator` + `skill-compiler` 是「近义聚类 → 生成 SKILL.md 草稿」
这条工作流的一半 —— 它与「记忆沉淀成可复用技能」是同一个产品方向。虽然现在零使用，但删掉等于放弃这个方向。
如果你确认短期不做「记忆→技能」，那就一起删（−172 行、−2 条命令），我按你的决定执行。

## 附：为什么现在不做「按专家共识直接删」

专家团看的是代码结构与使用证据，看不到你的路线意图。删除代码可逆（git），
但**放弃方向不可逆** —— 尤其 `skill-compiler` 属于「记忆 → 技能」这条主线。
所以我把可判定的部分（`atom.embedding`）直接做了，把需要路线判断的部分交回给你。
