# 文档维护规约：让文档不再落后于代码

> 这份文件回答一个问题：**改完代码，我怎么知道该改哪份文档？**
> 答案：不用靠记性 —— 跑 `npm run docs:check`，机器会告诉你。

## 一、为什么需要规约

本仓库踩过的坑不是「文档写得少」，而是**文档写得像规格，实际是愿景**：

- `docs/NEXUS-DESIGN.md` §5.5/§5.7/§7/§8 按 v0.2 设计稿写「已实现」，而代码只落了模块没接线（已修：逐条加了 `> ✅/⚠️/🧟/🗑️` 实现状态标注）；
- `runLifecycle`（权重衰减 / episode TTL）有实现、有单测，**全仓零调用点**，从未生效（已修：0.8.9 接到 `Facility.tickLifecycle`，同时删掉与之冲突的 episode TTL）；
- `coldArchive` / `sessionModeDefault` / `mode` 三个配置项被解析后**没人读**（已修：`coldArchive` 与 `mode` 已从 schema 删除，`sessionModeDefault` 现由 `SessionModeControl` 消费）；
- README 面板章节描述的是 `?panel=old` 的交互，而默认面板早已换成 BPanel（已修：0.8.9 删除旧面板，README 改写成单一实现）；
- `CHANGELOG.md` 停在 0.4.1，包已经是 0.8.x（本次修：补齐到当前版本）。

这类偏差的共同点：**人读文档看不出来，只有去代码里查调用点才能发现**。
所以规约的核心不是「多写文档」，而是把「文档说了什么」变成**可执行的断言**。

> 上面五条都是历史（每条后面标了它的结局）；其中前四条已由探针与本文档的门禁兜住，
> 第五条由这次补写的 CHANGELOG 兜住。把结局写在原地，是为了让「坑长什么样」可读，
> 同时让 `docs:check` 的叙述门禁（见第六节之二）能一眼看出这行讲的是历史。

## 二、三层结构

| 层 | 文件 | 谁维护 | 作用 |
|---|---|---|---|
| 唯一事实源 | `docs/status.json` | 人（改代码时一起改） | 每条能力：状态 + **处置** + 理由 + 文档出处 + 代码证据 + 若干探针 |
| 生成物 | `docs/IMPLEMENTATION-STATUS.md` | `npm run docs:status` | 人读的总表与待办清单；**不要手改** |
| 门禁 | `scripts/docs-status.mjs` | 人 | 校验「声明 == 代码事实」「生成物 == 注册表」「处置与状态相容」「**活文档没把已删除的符号当现有功能**」 |

**状态**回答「现在怎样」（✅/⚠️/🧟/❌）；**处置**回答「打算怎么办」（🔧 改代码 / 📄 改文档 / 🗑️ 删 / ⏸️ 推迟 / — 保持）。
两者分开记，是因为「没实现」和「不打算实现」是两件事，混在一起就永远分不清哪些是欠债、哪些是决定。

## 三、日常流程

### 改了 `src/` 的行为

```bash
npm run docs:check
```

- **通过** → 你的改动没有触碰任何已登记的能力，或者触碰了但状态没变。
- **失败** → 输出会直接点名哪条能力的哪个探针不符，例如：

  ```
  · runLifecycle — 有调用点(runLifecycle) in src：实测 true，声明 false
  ```

  意思是「你已经把生命周期接线了」，那就要去 `docs/status.json` 把
  `lifecycle-decay` / `lifecycle-episode-ttl` 的状态从 `dead` 改成 `implemented`，
  并删掉 `docs/NEXUS-DESIGN.md` §5.5 里对应的「未实现」标注。

### 新增或删除一个能力

1. 在 `docs/status.json` 的 `capabilities` 里增删条目（`group` 必须是 `groups` 里已有的）；
2. 每条至少一个探针；
3. `npm run docs:status` 重新生成总表；
4. 同步更新该能力在 `README.md` / `NEXUS-DESIGN.md` / `V0.5-DESIGN.md` 里的表述。

### 状态从 ❌/🧟 变成 ✅ 的那次提交

**必须同时删掉文档里对应的「未实现」表述。** 这是这份规约存在的全部意义：
状态表变绿而正文还在说「没做」，等于新的不一致。

## 四、处置决定：状态之外，还要写清「打算怎么办」

发现不一致之后，最容易犯的错是**逐条拍脑袋**决定「补代码还是改文档」。统一判据如下，**按顺序问，前两问是硬否决**：

| 顺序 | 问题 | 成立 → |
|---|---|---|
| **Q1** | **现状是不是缺陷？**（安全缺口 / 自相矛盾 / 功能死胡同） | 🔧 **改代码**。没有「以代码为准」的空间——把 bug 写成规格是荒谬的 |
| **Q2** | **文档的承诺与项目自己的原则或 §12 反目标冲突吗？** | 🗑️ **两边都删** |
| **Q3** | **这条承诺还有消费者或用户价值吗？** | 没有 → 🗑️ 删（没有消费者的机制就是死机制，这正是「反死机制」的本意） |
| **Q4** | 都不是 → 比成本：实现成本 vs 文档降级成本 | 默认偏 📄 **改文档** |

**为什么 Q4 默认偏「改文档」**：存在根本的不对称性——代码是**用户实际得到的行为**，文档是**意图**。
改文档成本≈0、可逆、零回归；改代码有回归风险且要长期维护。所以「以代码为准」是默认档，但它是默认，不是原则。

**「谁更优秀用谁」的正确版本**：不是比文档和代码谁写得漂亮，而是拿**项目自己的原则 + 用户价值**当裁判，去判「这条承诺」与「这个实现」哪个更站得住。

### 对「有代码未接线」的三个测试

| 测试 | 问法 | 不通过意味着 |
|---|---|---|
| **T1 用户价值** | 它承诺的东西今天还有人因此受损吗？ | 没人受损 → 不必须 |
| **T2 原则一致性** | 它与项目原则 / §12 反目标冲突吗？ | 冲突 → 不必须，**且该删** |
| **T3 副作用** | 接线后会造成新伤害吗？ | 会 → 要么加护栏再接，要么不接 |

**关键：「不必须」绝不等于「放着不管」。** 留在原地它既不是「实现」也不是「未实现」，
而是文档的持续谎言源——每次有人读到 §5.5 都会以为记忆真的会遗忘。
只有两个去处：`delete`（与原则冲突）或 `defer`（优先级低，但登记在案并写明触发条件）。

### 登记规则（机器强制）

- 每条能力必须有 `disposition`，取值见上；
- **非 `keep` 的必须写 `rationale`**（为什么这么处置），不写不让生成；
- **`keep` 当且仅当 `implemented`** —— 已经正确的功能不需要「改代码」，反过来没实现的功能也不该「保持现状」；
  其余组合由 `DISPOSITION_ALLOWS` 约束，写错直接报错退出。

处置落地后要回来改注册表：状态变了就改 `status`，改完把 `disposition` 改回 `keep`、删掉 `rationale`。

## 五、写探针的四条规矩

1. **只查运行事实，不查注释。** 注释会撒谎 —— `src/scanner.ts:24` 就写着
   `scannerRules=minimal`，而那个配置项根本不存在。这正是本表存在的理由。
2. **优先用 `symbol-called` 抓「有实现没接线」。** 它比较「符号出现次数」与
   「`function 符号(` 定义次数」，能直接抓出 `runLifecycle` 这类死代码。
3. **配置项要用「消费者探针」，不是「存在探针」。**
   查 `config.ts` 里有没有这个键没有意义（`coldArchive` 就在），
   要查它在 `src-except-config` 作用域里有没有被读取（`.coldArchive` 出现 0 次 → 死旋钮）。
4. **数字型断言要精确到区间。** 例如「Config 接口有几个旋钮」必须用
   `between` 把计数限制在接口体内，否则同文件其它接口的字段会被一起数进来。

## 六、探针种类

| kind | 语义 | 典型用途 |
|---|---|---|
| `symbol-called` | 作用域内该符号存在定义之外的调用点 | 抓死代码（当前只剩 `linkCluster`；`runLifecycle` 曾是） |
| `text-present` | 某文件/作用域是否匹配该正则 | 抓实现细节（`sessionId: 'host'`、`storeWritable: true`） |
| `count` | 匹配次数（可带 `between` 限定区间） | 清单条目数、旋钮数、调用点数量 |
| `file-exists` | 文件是否存在 | 旧面板组件 `src/ui/NexusPanel.tsx` 必须不存在 |

作用域：`src`（默认）、`src-except-config`（用于配置消费者探针）、`tests`、`bench`、`ci`。

### 六之二、探针之外的两道网

探针只能证明「登记过的代码事实没漂」——它证明不了**描述性文字**没漂。0.8.9 删掉旧面板之后，
README 的「已知限制」还留着**已删除入口**的老说法（「包内打包了三套面板实现（默认 B / `?panel=old` / `?panel=sample`）」），
而所有探针都是绿的：探针查的是 `src/` 里的调用点与字面量，没人去读那句话。
所以 `docs:check` 里另加了两条：

1. **叙述门禁**（`_removed_symbols`）：注册表登记一批**已删除的符号** —— `?panel=old` / `coldArchive` / `episode` TTL / `memory_trace` / `dsh-inject-scheduler` 等（完整清单见 `docs/status.json` 的 `_removed_symbols`），
   活文档（`README.md` / `docs/NEXUS-DESIGN.md` / 本文档）里再提到它们时，**同一行必须带一个豁免词**
   （已删除 / 已撤销 / 不再 / 不存在 / 历史上…），否则失败并点名行号。版本命名的设计文档
   （`docs/V0.x-*.md`）是当时的历史记录，故意不扫。这是在讲历史就补豁免词，不是历史就改内容 ——
   两种结局都比「读者以为它还在」好。
2. **零测试引用的模块现算**：README 的「反死机制」曾写死「另有 8 个运行时模块零测试引用」，
   增删一个模块就又过期。现在这个清单由 `docs-status.mjs` 的 `untestedModules()` 现算，
   写进 `docs/IMPLEMENTATION-STATUS.md` 的独立小节，README 只指向它。

> 门禁是网，不是证明：叙述门禁按**行**匹配豁免词，一行里恰好出现「不再」这种词就可能漏网
> （`NEXUS-DESIGN.md` §5.5 的冷迁移条目就这么漏过一次，靠人读才发现）。它的价值在于把
> 「已删除的东西被当成现有功能」这种最贵的错挡在提交之前。

> **注**：注册表用 JSON 而不是 YAML —— 本项目的依赖被刻意压到最小
> （`schemastery` + `zod`），为一个内部工具引入 YAML 解析器不划算，
> 而 Node 原生就能读 JSON。

## 七、门禁接在哪

| 位置 | 命令 | 效果 |
|---|---|---|
| 本地 | `npm run docs:check` | 手动校验 |
| 提交前 | `.githooks/pre-commit` | 漂移则拒绝提交（`--no-verify` 可显式绕过） |
| CI | `.github/workflows/ci.yml` | 漂移则红灯 |

## 八、这份规约自身的边界

- 探针覆盖的是**声明过的事实**，不是全部事实。没人登记的能力不会被检查 ——
  所以「新增能力必须登记」是人的责任，机器只保证「登记过的不许漂移」。
- `text-present` 查的是字面量，代码重构（改名、换写法）可能让探针失败而状态没变。
  这时**先确认状态**，再改探针的正则 —— 不要为了让它变绿而放宽到失去意义。
- 状态表是**快照式**的：它说「此刻代码是这样」，不承诺「以后也这样」。
  这也正是它需要跟着代码一起被更新的原因。
